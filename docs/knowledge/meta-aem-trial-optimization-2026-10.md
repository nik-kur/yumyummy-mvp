## 1. Причина неэлигибельности StartTrial

**Вердикт.** Не настройка AppsFlyer и не «нет Meta SDK как отправителя событий». У StartTrial почти нет событий с IDFA/ATE=true, а у событий без IDFA нет идентификатора инсталляции (anon_id), который Meta называет Install ID. Объём (7 событий за 28 дней, большинство sandbox) усиливает обе причины.

### 1.1. Определения Meta и AppsFlyer

- Meta, «Troubleshoot issues with app eligibility for AEM» [716239976391518](https://www.facebook.com/business/help/716239976391518): «Advertiser tracking enabled parameter volume out-of-range: you may see this if there are issues with the volume of events we received that have the advertiser tracking enabled parameter set to false or no… talk to your Meta account manager». «Install ID not detected or insufficient coverage: talk to your Meta account manager… reach out to your MMP». Отдельные причины: «Not enough signals from last 30 days», «Integration quality issue» (в т.ч. «low number of install events»), «Different integrations across multiple event types», «Multiple integrations for the same event» (выбор одной интеграции, перепроверка до 7 дней). Числовых порогов нет.
- AppsFlyer, «Meta Ads — AEM for iOS» [19228737402129](https://support.appsflyer.com/hc/en-us/articles/19228737402129-Meta-Ads-Aggregate-Event-Measurement-AEM-for-iOS), раздел «Troubleshooting ineligible events in Meta AEM»: Step 1 Advanced Data Sharing ON (Collaborate > Active Integrations > Meta Ads); Step 2 IP masking OFF (App Settings; «Events with masked IPs aren't eligible for AEM»); Step 3 S2S-события с IP + IDFV; **Step 4 «Review ATT consent rate: Meta accepts a limited volume of events with missing or zeroed-out IDFAs. If your app exceeds this threshold, you may see this error: Advertiser Tracking Enabled parameter volume out of range»**; Step 5 постбэки «Send all (including organic)»; «Still not working? Go to Meta's Event Manager… Select the affected app event. Set MMP traffic as the preferred connection method»; Meta отражает изменения через 2–3 дня.
- Meta, ATE: для App Events API / CAPI флаг `advertiser_tracking_enabled` (0/1) обязателен для каждого события; ATE=false → событие считается без ATT-разрешения; нет значения → использование ограничено; авто-вывод из ATT API есть только у Facebook SDK for iOS 17.0.0+ [365087497929660](https://www.facebook.com/business/help/365087497929660), [CAPI app events](https://developers.facebook.com/docs/marketing-api/conversions-api/app-events).
- Meta, Install ID: `anon_id` = «Your install ID. This field represents unique application installation instances» (user_data, не хэшировать) [CAPI app events](https://developers.facebook.com/docs/marketing-api/conversions-api/app-events); в Graph API `anon_id` = «The ID of a person who has installed the app anonymously», `app_user_id` «used internally by the iOS and Android SDKs» [application/activities](https://developers.facebook.com/docs/graph-api/reference/application/activities). Meta требует на custom app event хотя бы один из `advertiser_id` / `anon_id` / `attribution` / `ud` [facebook-ios-sdk#1303](https://github.com/facebook/facebook-ios-sdk/issues/1303).

### 1.2. Как ATE и Install ID идут по цепочке AppsFlyer → Meta

1. AppsFlyer SDK v6+ пишет ATT-статус (`att`: not_determined / restricted / denied / authorized; без IDFA поле заполняется нулями) на инсталл и события [360014090597](https://support.appsflyer.com/hc/en-us/articles/360014090597); поле `att` в raw data нужно запрашивать явно [208387843](https://support.appsflyer.com/hc/en-us/articles/208387843).
2. `timeToWaitForATTUserAuthorization` (у нас 60 с, промпт на welcome) держит install-постбэк до ответа на ATT или до таймаута. Гипотеза: инсталл пользователя, дошедшего до промпта позже 60 с, уходит без IDFA.
3. Интеграция AppsFlyer → Meta «always implements the Advertiser Tracking Enabled flag… no action is required of you in AppsFlyer» [207033826](https://support.appsflyer.com/hc/en-us/articles/207033826-Meta-Ads-integration-setup). Переключателя ATE нет.
4. Advanced data sharing ON → Meta получает инсталлы, app opens и in-app события всех устройств, включая без IDFA; payload «may include IP addresses, anon_ids (if available), vendor_id, and user agents» [19228737402129](https://support.appsflyer.com/hc/en-us/articles/19228737402129-Meta-Ads-Aggregate-Event-Measurement-AEM-for-iOS). OFF → только устройства с IDFA.
5. Гипотеза (сильная): anon_id генерирует Meta SDK; бинарник AppsFlyer iOS SDK 6.18.0 в проекте содержит строки `com-facebook-sdk-PersistedAnonymousID.json`, `retrievePersistedAnonymousID`, `fb_anon_id` — то есть AppsFlyer читает anon_id из файла Meta SDK, а без Meta SDK его нет. RevenueCat документирует ту же зависимость: `$fbAnonId` берётся из `AppEvents.shared.anonymousID`, Meta нужен хотя бы один из `$fbAnonId` / `$idfa` [revenuecat meta-ads](https://www.revenuecat.com/docs/integrations/attribution/meta-ads). Следствие: StartTrial без IDFA приходит в Meta только с IDFV + IP → «Install ID not detected / insufficient coverage».
6. Итог по нашим данным: IDFA есть у ≈16% установок (PostHog) и ≈8% инсталлов в Meta; из 7 триалов за 30 дней ATT granted только у тест-устройства основателя. У StartTrial доля ATE=false близка к 100% при 7 событиях → обе причины Meta.

Спорное: Meta формулирует причину как «объём событий с ATE=false», AppsFlyer — как «доля событий без IDFA превысила порог». Какая из трактовок (доля или абсолют) применяется, неизвестно; при 7 событиях это неразличимо.

Плагин: [appsflyer-react-native-plugin#619](https://github.com/AppsFlyerSDK/appsflyer-react-native-plugin/issues/619) (6.15.3–6.17.1): `advertiserIdEnabled=false` при `att_status=3`; закрыт как stale без ответа; в changelog 6.17.x–6.18.0 фикса нет. У нас `react-native-appsflyer ^6.18.0`. Гипотеза: не доказано, что ATE в постбэке Meta выводится из этого поля; вопрос в саппорт AppsFlyer.

Ошибка #3955014: нет в справочнике ошибок Marketing API ([ios-14-error-codes](https://developers.facebook.com/docs/marketing-api/error-reference/ios-14-error-codes/)), MCP `ads_get_errors` пуст; это creation-time валидация Ads Manager поверх вердикта Events Manager, отдельного лекарства нет. Community-кейс с идентичной связкой (AppsFlyer S2S → Meta, без Meta SDK, та же формулировка): [stackoverflow 79750714](https://stackoverflow.com/questions/79750714/how-to-fix-the-facebooks-advertiser-tracking-enabled-parameter-volume-out-of-range) (не прочитан, fetch заблокирован).

## 3. Meta SDK рядом с AppsFlyer

- Для AEM app promotion с MMP Facebook SDK не требуется; для AEO нужен FB SDK или MMP плюс eligibility приложения [2308889442692949](https://www.facebook.com/business/help/2308889442692949).
- Риски двух интеграций: «different integrations across multiple event types» (optimization-событие через другую интеграцию, чем install → неэлигибельно для AEO/VO) и «multiple integrations for the same event» (двойной счёт, выбор одной интеграции, перепроверка до 7 дней) [716239976391518](https://www.facebook.com/business/help/716239976391518); AppsFlyer: «Meta ads doesn't de-duplicate in-app events that are reported from both SDKs» [4410481130641](https://support.appsflyer.com/hc/en-us/articles/4410481130641-Meta-ads-discrepancies); Meta: каждое событие только через один канал [251324098890446](https://www.facebook.com/business/help/251324098890446); Meta SDK автологирует App Install, App Launch и In-App Purchase (sandbox тоже) [getting-started-app-events-ios](https://developers.facebook.com/docs/app-events/getting-started-app-events-ios/); гайд Singular по сосуществованию: `FacebookAutoLogAppEventsEnabled = false` [360030530092](https://support.singular.net/hc/en-us/articles/360030530092).
- Нюанс (гипотеза из п. 1.2.5): «молчащий» Meta SDK (autolog off, без логирования событий) даёт AppsFlyer anon_id, который она пересылает «if available», и мог бы закрыть причину «Install ID not detected», не создавая второй поток событий. Нужен нативный билд (react-native-fbsdk-next), значит не раньше 1.0.11, и только после подтверждения AppsFlyer, что anon_id действительно уходит в постбэки.
- Вердикт: сейчас нет. В 1.0.11 рассмотреть только «молчащий» режим и только после ответа AppsFlyer.

StartTrial-оптимизация = отдельная кампания.
- AEM-репортинг близок к real-time, окна для AEO/VO 1-day или 7-day click [3499572073626051](https://www.facebook.com/business/help/3499572073626051); StartTrial по креативам читать в Ads Manager (`conversions:start_trial_mobile_app`), ground truth — AppsFlyer/Adapty.
- Пороги: learning phase ≈50 optimization events за 7 дней после последней значимой правки; Learning limited «not a penalty», показы идут; совет Meta — более частое событие [269269737396981](https://www.facebook.com/business/help/269269737396981), [112167992830700](https://www.facebook.com/business/help/112167992830700). Практики (гипотезы): ≈10 событий/день на ad set [adapty scaling guide](https://adapty.io/blog/scale-meta-ads-for-subscription-apps/); событие в первые 24 ч после инсталла при 7-дневном окне AEM [revenuecat / Burke](https://www.revenuecat.com/blog/growth/meta-ads-in-2025-tips-for-apps). У нас 2 FB-триала/30д; при 1,6% install→trial для 50 триалов/нед нужно ≈3000 инсталлов/нед.
- Условия возврата к StartTrial: (а) StartTrial eligible в Events Manager; (б) ≈30+ реальных StartTrial за 30 дней по всем источникам как ориентир для перепроверки (гипотеза; AppsFlyer шлёт «all including organic», Meta просит слать все источники [251324098890446](https://www.facebook.com/business/help/251324098890446), значит рост пейвольной конверсии и ASA/organic тоже работают на eligibility); (в) после eligibility запускать отдельную StartTrial-кампанию малым бюджетом параллельно инсталльной и принимать Learning limited; переводить основной бюджет при ≥50 триалов/нед.
- SKAN как промежуточный вариант: технически можно (добавить событие в SKAN config; StartTrial уже в схеме) [2308889442692949](https://www.facebook.com/business/help/2308889442692949); но crowd anonymity ≈15 инсталлов/24 ч на SKAN campaign ID (оценка Singular, файл строки 2659–2660, 2581), Meta может мапить несколько ID на кампанию; при ~4 инсталлах/день CV = null; задержка ≥24 ч, в Ads Manager только postback 1 с fine value, ad set/ad моделируются [584603712214119](https://www.facebook.com/business/help/584603712214119); окна SKAN 4: 0–2 дня + 24–48 ч, далее + 24–144 ч [Apple](https://developer.apple.com/documentation/storekit/receiving-postbacks-in-multiple-conversion-windows); SKAN-only ad set ограничивает AppsFlyer [19228737402129](https://support.appsflyer.com/hc/en-us/articles/19228737402129-Meta-Ads-Aggregate-Event-Measurement-AEM-for-iOS). Singular (видео 8, строки 2625–2638): без AEM-eligibility остаётся только SKAN; (видео 10, строка 3030): оба типа атрибуции пишутся всегда, выбор влияет только на delivery. Вердикт: не запускать.

## 5. Adapty Attribution

- Механика [meta-create-campaign](https://adapty.io/docs/meta-create-campaign.md), [ua-facebook](https://adapty.io/docs/ua-facebook.md): objective Sales, conversion location Website, Website URL `https://api-ua.adapty.io/api/v1/attribution/click` + URL parameters из Click link, dataset = web-пиксель из Events Manager, performance goal «Maximize number of conversions» на Purchase / Start trial. iOS-матчинг только вероятностный (IP-диапазон + ОС + время/язык/страна; окно по умолчанию 6 ч, 1–24 ч); отключить вероятностный = iOS без атрибуции. Опции: Qualified trial (держит Trial started 1–24 ч, не шлёт при отмене), Revenue override, Predicted LTV (≥100 Meta-атрибутированных конверсий/нед 4 недели подряд, ≥5 разных значений), «Send all events» (не рекомендуется). Предупреждение Adapty: если MMP тоже шлёт trial_started в тот же пиксель, Meta получит триал дважды. Один источник атрибуции на профиль, смена только в первые 15 минут [attribution-integration](https://adapty.io/docs/attribution-integration.md).
- Почему обходит AEM: website-conversion кампании не требуют AEM-eligibility [331612538028890](https://www.facebook.com/business/help/331612538028890); Meta сама допускает App Store как destination Sales-кампании («Website and app», backup destination App store) [316567509947154](https://www.facebook.com/business/help/316567509947154) и app-ads с website-destination [1443700713009775](https://www.facebook.com/business/help/1443700713009775).
- Состояние: доступ к Attribution есть (CLI работает), SDK-флаг в проде (1.0.10), 233 инсталла/30д регистрируются, Meta не подключена, 122 FB-инсталла видны как organic.
- Подводные камни: другой тип кампании и аукцион, лишний редирект (гипотеза: падение на переходе); вероятностный матчинг на iOS и открытый вопрос Apple-политики (гипотеза); дедупликация: AppsFlyer → app dataset, Adapty → web pixel, не пересылать одни события в один пиксель, в отчётах триалы будут считаться дважды; объём: 50/нед learning, Qualified trial режет ещё, pLTV недостижим; ASA spend в Attribution нет.
- Вердикт: не вместо AppsFlyer. Как параллельный эксперимент возможен без билда: отдельная Sales-кампания с Adapty click link и своим пикселем, малый бюджет, сравнение CPI/CPT с инсталльной; это не решает eligibility StartTrial в app dataset.

## Чеклист без билда (неделя 7–14 октября)

1. Events Manager → Check app eligibility: зафиксировать дату и причины по Install / StartTrial / Subscribe / CompleteRegistration.
2. AppsFlyer App Settings: IP masking OFF. Meta Ads integration: Advanced Data Sharing ON, постбэки «Send all (including organic)».
3. Events Manager: StartTrial и Subscribe → «Set MMP traffic as the preferred connection method»; через 2–3 дня повторить п. 1.
4. У StartTrial попробовать «More details» → «Continue setup».
5. Тикет AppsFlyer (anon_id в постбэках, доля ATE=true по af_start_trial, issue #619 при 6.18.0). Тикет Meta с Dataset ID и обеими причинами.
6. Прекратить sandbox-покупки на продакшн-сборке до 1.0.11.
7. Выгрузить raw data installs + in-app events с полем `att`; посчитать долю authorized отдельно по af_start_trial.
8. Ads Manager: удалить черновик `zz_TEST_deleted_AEM_probe` (discard draft) в кампании 120249752139630513.
9. Кампания: installs, одна кампания, один широкий ad set; SKAN-only ad set не создавать.

## В билд 1.0.11

1. ATT: гарантировать промпт до истечения `timeToWaitForATTUserAuthorization` (60 → 120 с, если путь до welcome может быть дольше, рекомендация AppsFlyer [integrate-ios-sdk](https://dev.appsflyer.com/hc/docs/integrate-ios-sdk)); пересмотреть pre-ATT экран: доля ATE=true — единственный рычаг на обе причины в наших руках.
2. Sandbox: не логировать af_start_trial/af_subscribe для sandbox-транзакций, либо перенести события на Adapty → AppsFlyer с токеном в поле Sandbox [adapty appsflyer](https://adapty.io/docs/appsflyer.md) (серверные события должны нести IP + IDFV), либо AppsFlyer receipt validation (`validateAndLog`, iOS SDK ≥6.17.8, sandbox → af_purchase_sandbox_sdk) [42137474889489](https://support.appsflyer.com/hc/en-us/articles/42137474889489). Один источник события, без дублей.
3. Обновить react-native-appsflyer, перепроверить `advertiserIdEnabled` при authorized.
4. Advanced Matching: передавать SHA-256 email после регистрации [47876839961489](https://support.appsflyer.com/hc/en-us/articles/47876839961489-Advanced-Matching-Data-Sharing) (гипотеза: улучшит матчинг без IDFA).
5. Высокочастотное событие выше по воронке (paywall shown / onboarding completed) → Meta как промежуточная ступень оптимизации (гипотеза).
